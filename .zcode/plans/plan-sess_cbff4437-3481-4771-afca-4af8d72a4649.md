# HakkuAuto — Scraper + Auto-redeem de códigos gacha

## Contexto
Proyecto greenfield (directorio vacío, sin git). Herramienta personal que: 1) scrapea códigos de regalo de juegos gacha (Blue Archive hoy, Stella Sora hoy, más juegos mañana), 2) los muestra en una WebUI temática por juego, 3) los canjea automáticamente a las cuentas configuradas. Stack obligatorio: NestJS + React **en una sola carpeta/proyecto**, deploy Docker, arquitectura **DDD + hexagonal estricta** (requisito del usuario, no negociable), Ponytail para minimizar cada pieza dentro de esa estructura. Git con commits por milestone. Al final: AGENTS.md, react-doctor, ponytail-audit, graphify.

## Hallazgos de investigación (condicionan el diseño)
- **Rentry BA**: el modo `/raw` está gated con `SECRET_RAW_ACCESS_CODE` → el scraper parsea el **HTML renderizado** de `rentry.org/CouponBA` (funciona server-side). Códigos como `### HANAWOTADOTTE` + fecha de validez compartida en la página.
- **Stella Sora fuentes**: web oficial `/news` es SPA pura (JS-only); **VG247 es server-rendered** con formato limpio (lista `CODE — reward`, sección separada de expirados); GameRant similar. Adapter primario VG247/GameRant + intento timeboxed de descubrir la API JSON de la SPA oficial desde su bundle (`novaweb-usstatic.yo-star.com/h5/assets/`).
- **BA canje** (`mcoupon.nexon.com/bluearchive`): servidor + member code + cupón; **sin captcha** en esa vía (el SMS es solo para la pestaña "consulta"). Endpoints exactos: se extraen del JS de la página en implementación y se documentan.
- **SS canje** (`stellasora.global/gift`): SPA, servidor + UID + código, posible captcha. Si el endpoint requiere captcha/token → adapter devuelve `NEEDS_MANUAL` y la UI ofrece asistencia manual (copiar código + deep link al sitio oficial).

## Arquitectura (clean-ddd-hexagonal)
4 capas, dependencias solo hacia adentro (presentation/infrastructure → application → domain):

- **domain/** — puro, cero imports de Nest: agregados `GameCode` y `GameAccount`, value objects (`CodeKey`, `ServerId`, credenciales), puertos de repositorio junto a cada agregado, domain events (`CodeDiscovered`, `CodeRedeemed`, `RedeemFailed`), errores de dominio.
- **application/** — use cases + puertos driven definidos aquí: `CodeSourcePort` (scrapers), `RedemptionGatewayPort` (canjes), `EventPublisherPort`. Use cases: `ScanGameCodes`, `RedeemCodeToAccount`, `RedeemPendingCodes`, CRUD de cuentas, queries de lectura para la UI.
- **infrastructure/** — adapters: SQLite (repos + mappers, better-sqlite3), HTTP client con UA, **plugins de juego**, scheduler (@nestjs/schedule), EventEmitter2 como EventPublisher.
- **presentation/** — controllers REST de Nest + ServeStatic del build de React.

**Seam de juegos (clave para "añadir más juegos")**: interfaz `GamePlugin` = definition (metadata: nombre, arte oficial, banner, colores/tema, lista de servidores, schema de campos de cuenta) + source adapters + redemption adapter, todo en `src/infrastructure/games/<game-id>/`. Añadir un juego = 1 carpeta nueva + registro en el `GameRegistry`; **cero cambios en core y UI genérica se adapta sola** desde la metadata.

Un solo `package.json`: `npm run dev` (Nest watch + Vite dev proxy), build = Vite → `dist/webui` servido por Nest (ServeStaticModule). Una imagen Docker.

## Flujo principal
Cron (30 min, configurable por env) → por cada juego habilitado `ScanGameCodes` → fuentes normalizan entradas → dedupe por (gameId, code) → persistir → evento `CodeDiscovered` → `RedeemPendingCodes` → para cada cuenta con `autoRedeem=true` → `RedemptionGatewayPort.redeem(account, code)` → registrar `RedemptionRecord` (estados: SUCCESS / ALREADY_USED / EXPIRED / INVALID_CODE / NEEDS_MANUAL / FAILED + mensaje raw) con delay de cortesía entre canjes del mismo juego.

## API REST (`/api`)
- `GET /games` (metadata completa para theming) · `GET /games/:id/codes` · `POST /games/:id/scan`
- `GET|POST|PATCH|DELETE /games/:id/accounts` (credenciales validadas contra schema del plugin)
- `POST /games/:id/accounts/:accId/redeem` (manual, opcional `codeIds`) · `GET /redemptions?gameId=&status=`
- Errores de dominio → exception filter → HTTP semántico.

## WebUI
- **Dashboard**: cards por juego con arte oficial de banner, contadores de códigos activos y cuentas, estado del último scan.
- **GamePage**: lista de códigos con estado, badge de reward, botón scan/redeem manual, feed de historial.
- **AccountConfigPage personalizada por juego**: hero con arte oficial + acentos de color del plugin, campos según schema (BA: selector servidor + member code con guía ilustrada; SS: servidor + UID con guía), toggle auto-redeem, historial por cuenta.
- i18n bilingüe con toggle persistido; diccionarios JSON planos para que añadir idioma sea trivial.
- Datos de theming vienen de `GET /api/games` → la UI genérica se viste sola; `webui/src/games/<gameId>/` añade personalizaciones específicas.

## Implementación (orden y commits)
1. `chore: scaffold` — git init, package.json único, tsconfig, Nest bootstrap, Vite scaffold, ESLint.
2. `feat(domain)` — agregados, VOs, eventos, errores + tests de invariantes.
3. `feat(application)` — puertos + use cases con adapters in-memory.
4. `feat(infra-persistence)` — SQLite schema + mappers + repos.
5. `feat(games)` — registry, plugin BA (rentry source; descubrir endpoints mcoupon con curl, implementar redeem, documentar en docs/), plugin SS (VG247 source; gift redeem con detección de captcha → NEEDS_MANUAL).
6. `feat(scheduler)` — cron + event wiring full-auto con toggles.
7. `feat(api)` — controllers + filters.
8. `feat(webui)` — i18n, páginas, theming por juego.
9. `feat(deploy)` — Dockerfile multi-stage + compose + .env.example.
10. `docs: AGENTS.md` — propósito, reglas de capas, guía "añadir un juego en N pasos", comandos, convenciones.

## Verificación
- **Unit**: invariantes de dominio (transiciones de GameCode, dedupe, validación de credenciales por schema) y use cases con adapters in-memory — un check por lógica no trivial (estilo ponytail).
- **Live E2E**: levantar server → `POST /games/blue-archive/scan` contra rentry real → verificar códigos en API y UI (browser check). Canje real solo si el usuario aporta member code/UID de prueba; si no, adapter verificado contra respuestas reales documentadas de docs/.
- **Docker**: build + `compose up` + smoke test de UI servida.
- **Pasos finales obligatorios**: `react-doctor` (webui) → corregir; `ponytail-audit` (repo completo) → corregir; `graphify` al cierre.
